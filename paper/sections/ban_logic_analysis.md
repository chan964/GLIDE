# BAN Logic Security Analysis
## L-ECQV + DID Authentication Protocol

### 1. Principals and Notation

| Symbol | Meaning |
|--------|---------|
| D | Device (constrained IoT node) |
| G | Gateway |
| I | Issuer (CA running did:web registry) |
| P\|≡X | P believes X |
| P\|~X | P once said X |
| P◁X | P sees X |
| #(X) | X is fresh (contains a nonce) |
| P\|⇒X | P has jurisdiction over X |
| {X}K | X encrypted/signed under key K |
| K(P) | Public key of P |
| K⁻¹(P) | Private key of P |
| K(D,G) | Session key shared between D and G |
| Q_dev | Device's reconstructed public key |
| Q_ca | Issuer's public key (pinned at G) |

---

### 2. Protocol Idealization

Before applying BAN rules, we idealize the protocol into BAN form.

**MSG_1 (Device → Gateway):**
D → G: {E_d, nonce_d, R, cert_info}_{K⁻¹(D)}
D signs (E_d ∥ R ∥ cert_info ∥ nonce_d) with its long-term private key K⁻¹(D).

**MSG_2 (Gateway → Device):**
G → D: {E_g, nonce_g}_{K⁻¹(G)}, bound to MSG_1
G signs (MSG_1 ∥ E_g ∥ nonce_g) with its long-term private key K⁻¹(G).

**Session key derivation (both sides):**
K(D,G) = HKDF(SHA256(MSG_1 ∥ MSG_2), ECDH(e_d, E_g))

---

### 3. Initial Assumptions

These hold from the provisioning phase (factory provisioning + pinned bootstrap):

| # | Assumption | Justification |
|---|-----------|---------------|
| A1 | G\|≡ I\|⇒ Q_dev | Gateway trusts issuer's authority on device public keys. Established during pinned bootstrap: gateway pins Q_ca and trusts certificates signed by I. |
| A2 | G\|≡ #(nonce_d) | nonce_d is fresh: generated by D using CSPRNG per session. Gateway verifies freshness by checking cert_info timestamp window. |
| A3 | D\|≡ K(G) | Device pre-provisioned with gateway's public key at manufacture (in credentials.h). |
| A4 | D\|≡ #(nonce_g) | nonce_g is fresh: generated by G using CSPRNG per session, bound to this MSG_2 via transcript signature. |
| A5 | G\|≡ I has K⁻¹(I) | Gateway trusts issuer holds its own private key (implicit in the CA model). |
| A6 | I\|≡ D has K⁻¹(D) | Issuer verified device identity during provisioning before issuing certificate. |

---

### 4. BAN Inference Rules Used

**R1 — Message Meaning Rule:**
P|≡ K(Q,P),  P◁{X}_{K⁻¹(Q)}
─────────────────────────────
P|≡ Q|~X
If P believes Q's public key is K(Q), and P sees X signed by K⁻¹(Q), then P believes Q once said X.

**R2 — Nonce Verification Rule:**
P|≡ #(X),  P|≡ Q|~X
────────────────────
P|≡ Q|≡ X
If P believes X is fresh and Q once said X, then P believes Q currently believes X.

**R3 — Jurisdiction Rule:**
P|≡ Q|⇒X,  P|≡ Q|≡X
────────────────────
P|≡ X
If P believes Q has authority over X and Q believes X, then P believes X.

**R4 — Seeing Rule:**
P◁(X, Y)
─────────
P◁X
If P sees (X, Y), P sees X.

---

### 5. ECQV Reconstruction Lemma

Before deriving the authentication goals, we establish a key lemma specific to our protocol's use of ECQV implicit certificates.

**Lemma (ECQV Correctness):**
Given R and cert_info in MSG_1, the gateway can compute:
e = SHA256(R ∥ cert_info)
Q_dev = e × R + Q_ca
By the ECQV reconstruction identity, d × G = Q_dev, where d is D's private key.
Therefore, a valid ECDSA signature under K⁻¹(D) = d verifies under the reconstructed Q_dev.

**Consequence for BAN:** The gateway reconstructing Q_dev from (R, cert_info, Q_ca) is equivalent to retrieving K(D) from a trusted source (the issuer I). Under assumption A1, this reconstruction is trusted.

Formally:
G|≡ I|⇒ Q_dev,  G◁(R, cert_info),  G|≡ Q_ca = K(I)
──────────────────────────────────────────────────────
G|≡ Q_dev = K(D)                          ... (L1)

### 6. Goal Derivations

#### Goal G1: Gateway Authenticates Device

**G1: G|≡ D|≡ (D is the originator of MSG_1)**

**Step 1:** G receives MSG_1 and extracts the signature.
G◁ {E_d, nonce_d, R, cert_info}_{K⁻¹(D)}           (received MSG_1)

**Step 2:** By Lemma L1, G has reconstructed K(D) = Q_dev.
G|≡ Q_dev = K(D)                                     (from L1)

**Step 3:** Apply R1 (Message Meaning Rule):
G|≡ K(D),  G◁{E_d, nonce_d, R, cert_info}_{K⁻¹(D)}
────────────────────────────────────────────────────
G|≡ D|~ (E_d, nonce_d, R, cert_info)                 (D once said this)

**Step 4:** Apply R2 (Nonce Verification) using A2:
G|≡ #(nonce_d),  G|≡ D|~ (E_d, nonce_d, R, cert_info)
───────────────────────────────────────────────────────
G|≡ D|≡ (E_d, nonce_d, R, cert_info)                  (D currently believes this)

**Step 5:** Since the signature covers E_d (D's ephemeral key for this session), G now believes D generated E_d in this session.
G|≡ D|≡ (E_d is D's contribution to K(D,G))           ✓ G1 PROVED

---

#### Goal G2: Device Authenticates Gateway

**G2: D|≡ G|≡ (G is the originator of MSG_2)**

**Step 1:** D receives MSG_2.
D◁ {E_g, nonce_g}_{K⁻¹(G)}, bound to MSG_1

**Step 2:** D has pre-provisioned K(G) from credentials.h (assumption A3).
D|≡ K(G)                                              (from A3)

**Step 3:** Apply R1:
D|≡ K(G),  D◁{MSG_1, E_g, nonce_g}_{K⁻¹(G)}
────────────────────────────────────────────
D|≡ G|~ (MSG_1, E_g, nonce_g)                         (G once said this)

**Step 4:** Apply R2 using A4:
D|≡ #(nonce_g),  D|≡ G|~ (MSG_1, E_g, nonce_g)
────────────────────────────────────────────────
D|≡ G|≡ (MSG_1, E_g, nonce_g)                         (G currently believes this)

**Step 5:** Since MSG_1 is bound in G's signature, D knows G saw and verified MSG_1 before responding.
D|≡ G|≡ (G authenticated D before generating E_g)     ✓ G2 PROVED

---

#### Goal G3: Session Key Freshness and Exclusivity

**G3: D|≡ G|≡ K(D,G)  AND  G|≡ D|≡ K(D,G)**

The session key is:
K(D,G) = HKDF(SHA256(MSG_1 ∥ MSG_2), ECDH(e_d, E_g))

**Freshness argument:**
- e_d is fresh (generated by D per session, included in signed MSG_1)
- e_g is fresh (generated by G per session, included in signed MSG_2)
- The transcript SHA256(MSG_1 ∥ MSG_2) binds both contributions
- Therefore K(D,G) is fresh and unique to this session

**Exclusivity argument:**
- K(D,G) requires ECDH(e_d, E_g) = e_d × E_g = e_g × E_d
- e_d is known only to D (never transmitted)
- e_g is known only to G (never transmitted)
- An adversary who does not know either scalar cannot compute K(D,G)
- This reduces to the ECDH hard problem (CDH assumption on P-256)
D|≡ #(e_d),  G|≡ #(e_g),  CDH assumption on P-256
──────────────────────────────────────────────────
D|≡ G|≡ K(D,G)  ∧  G|≡ D|≡ K(D,G)                   ✓ G3 PROVED

---

### 7. Summary

| Goal | Statement | Result |
|------|-----------|--------|
| G1 | Gateway authenticates Device via ECQV reconstruction + ECDSA | ✓ Proved |
| G2 | Device authenticates Gateway via pre-provisioned key + ECDSA | ✓ Proved |
| G3 | Session key is fresh, exclusive to D and G | ✓ Proved under CDH |

**Security assumptions required:**
- ECDSA unforgeability under chosen-message attack (EU-CMA)
- Computational Diffie-Hellman (CDH) hardness on P-256
- SHA-256 collision resistance (for transcript binding)
- Issuer key integrity (Q_ca correctly pinned at bootstrap)

**Explicit limitations of BAN analysis:**
BAN logic assumes ideal message transmission and does not model computational complexity, timing attacks, or side-channel vulnerabilities. The CDH assumption in G3 is stated informally; a full computational proof would require the random oracle model. These are acknowledged as future work.
